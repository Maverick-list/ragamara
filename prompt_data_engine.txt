## DATA SOURCE A — DAPOBUD

Official website:

https://dapobud.kemenbud.go.id/

DAPOBUD stands for Data Pokok Kebudayaan and is managed by Indonesia's Ministry of Culture.

It serves as the primary official reference for cultural data.

Our goal is to extract available public records containing:

1. Official cultural name.
2. Geographic region.
3. Cultural category.
4. Entity type.
5. Official record identifier, when available.
6. Official record URL.
7. Other useful metadata provided by the source.

Important distinction:

DAPOBUD contains several cultural entity types, including:

- Objek Pemajuan Kebudayaan (OPK).
- Warisan Budaya Takbenda (WBTb).
- Cagar Budaya.
- Objek Diduga Cagar Budaya.
- Sumber Daya Manusia Kebudayaan.
- Lembaga Kebudayaan.
- Sarana dan Prasarana Kebudayaan.

Do not mix these entity types into one indistinguishable category.

For the initial RAGAMARA cultural learning database, prioritize:

- Objek Pemajuan Kebudayaan (OPK).
- Warisan Budaya Takbenda (WBTb).

Make the target entity types configurable so additional datasets can be added later.

Preserve the official classification exactly as presented by DAPOBUD.

Do not assume that a particular DAPOBUD endpoint, field, or page structure exists until verified.

MediaWiki API endpoint:

https://id.wikipedia.org/w/api.php

- Available data fields.

# 7. PHASE D — WIKIPEDIA INDONESIA MEDIAWIKI ENRICHMENT

Use the official MediaWiki Action API.

API endpoint:

https://id.wikipedia.org/w/api.php

Use standard GET requests for read-only operations.

Do not scrape Wikipedia HTML when the API provides the required information.

## STEP 1: Search for the cultural article

For each DAPOBUD record:

Use the official cultural name as the initial search query.

Suggested Action API parameters:

action=query
list=search
srsearch=<CULTURAL_NAME>
srnamespace=0
srlimit=5
format=json
formatversion=2

Perform matching in the Indonesian Wikipedia namespace.

Do not automatically select the first search result.

Retrieve available candidate titles and relevant snippets.

## STEP 2: Candidate matching

Implement a dedicated matching module.

Compare:

- Original cultural name.
- Normalized cultural name.
- Candidate Wikipedia title.
- Alternative spelling, if verifiable.
- Regional context.
- Relevant article content.

Normalization may include:

- Unicode normalization.
- Case folding.
- Whitespace normalization.
- Punctuation normalization.
- Consistent handling of diacritics without discarding the original text.

Use exact title matching as the strongest signal.

Fuzzy matching may use RapidFuzz or Python's standard difflib.

Suggested confidence rules:

| Matching result | Status |
|---|---|
| Unique exact title match | High confidence |
| Exact normalized title match | High confidence, subject to contextual validation |
| Very close fuzzy match | Requires review |
| Several similarly ranked candidates | Ambiguous |
| Weak similarity | No automatic match |

Use configurable scoring thresholds.

Never merge ambiguous candidates automatically.

Keep alternative candidates and matching evidence for manual review.

A matching cultural name is not sufficient when the candidate article clearly describes a different object, individual, place, or event.

## STEP 3: Retrieve article data

For a validated candidate, request:

action=query
prop=extracts|pageimages|info
titles=<MATCHED_TITLE>
explaintext=1
exintro=0
redirects=1
inprop=url
piprop=thumbnail|original|name
pithumbsize=1000
format=json
formatversion=2

Adapt parameters to the API response and available extension support.

Extract:

- Page ID.
- Canonical title.
- Full page URL.
- Plain-text extract.
- Thumbnail URL.
- Original image URL when provided.
- Image filename when available.
- Redirect information if relevant.

Store a clean article extract.

Preserve paragraph boundaries where practical.

Avoid saving raw HTML in the final JSON.

Set reasonable length limits for very long descriptions and record whether truncation occurred.

Do not invent historical summaries from an article title.

## STEP 4: Image metadata

If an image is returned:

Retrieve additional image metadata using MediaWiki's imageinfo capability.

Use:

prop=imageinfo
iiprop=url|extmetadata

Retrieve, when available:

- Original image URL.
- Thumbnail URL.
- File title.
- Wikimedia file description page.
- Image author or creator.
- License name.
- License URL.
- Attribution requirement.
- Relevant descriptive metadata.

Do not assume that every image is freely usable merely because it appears on Wikipedia.

If licensing information is missing, mark it as unknown and require manual verification.

Do not download and redistribute images unless their applicable licenses and conditions permit it.

For RAGAMARA, save image links and attribution metadata rather than copying unrestricted image assets into the frontend.

## STEP 5: Source attribution

For each matched article, retain:

- Wikipedia article title.
- Article URL.
- Wikipedia project.
- Retrieval timestamp.
- Relevant article revision identifier, if obtainable.
- Applicable article license information.

For images, retain independent image-level attribution and license metadata.

Keep the original source link visible in the final record.

## STEP 6: No-match behavior

If a candidate cannot be reliably matched:

Do not fabricate an article.

Do not substitute another similar cultural entry.

Set:

wikipedia.status = "no_match"

Keep the DAPOBUD record.

Allow future manual enrichment.
